Every submitted listing needs a verified PDP in url, including Amazon. Use exact field names, types, allowed values, and request structure from the fixed external contract. 4 required AI roles + 1 optional

Two Azure AI Foundry deployments. One software-controlled workflow. A2 alone has a bounded tool-selection loop.

Terra: discovery and scraper inputs. Luna: intent, returned data, and optional explanation. Reuse these roles across products and retailers; they are functions in one application, not separate services or agent conversations that delegate to one another.

Software owns acceptance and execution

The backend validates schemas, source evidence, exact identity, variants, quantity, PDPs, and location. It selects final competitors and offers, invokes scrapers, records provider jobs, prevents duplicates, applies retries/cancellation, calculates metrics, and decides final status. No model can approve its own output, change the frozen setup, invent an ID, or extend a budget. Competitors and sellers stay read-only.

Minimal Azure execution

Use direct model calls through the official SDK and Responses API with fixed prompts and structured outputs. A2 uses strict tool arguments with parallel_tool_calls: false; software still schedules independent workflow work within shared limits. Foundry Agent Service and another agent framework are not required. Keep one codebase and one persisted workflow. For a fresh Azure implementation, one Azure Functions app with Durable Functions is the proposed background runtime: outbound calls run in activities and waiting uses durable timers. Keep the orchestrator deterministic. Activities can repeat, so provider reconciliation and duplicate-safe writes remain required. Persist business state separately from model conversations and reference large raw evidence by ID.

Conservative initial capacity

Application-wide: at most 2 Luna calls + 2 Terra calls across all workers/replicas. Per run/draft: at most 2 concurrent model calls across both models combined. One active analysis/recovery run per customer analysis workspace. Per external provider account: at most 2 active HTTP calls and 2 outstanding accepted or acceptance-uncertain collection jobs, or lower vendor limits. Pending or uncertain jobs keep their slots until verified completion/cancellation, confirmed non-acceptance, or provider-confirmed expiry. Use the existing runtime/storage for capacity controls. Recover temporary request reservations after crashes using saved operation IDs and expiry tied to the bounded request lifetime. Exhausted job reconciliation reports a blocker; it never creates endless polling or a duplicate submission. These settings require quota checks and load tests before release.

Configure finite phase/run query, candidate, page, tool/model-call, input/output-token, spend, and time limits. Reserve capacity and allowance before dispatch; waiting does not reset deadlines. Use compact evidence, structured extraction first, verified PDP reuse, and one normalization per record or small identified batch. A3 receives only the selected retailer schema and verified facts; A4 receives only the internal result schema and relevant record/context. Do not send all contracts, the workflow document, or unrelated history. Keep only the current A2 task, compact evidence, visited/rejected identifiers, and API-required active tool state. Use the lowest supported reasoning effort that passes evaluation and count reported reasoning tokens in billed usage. Model assignments stay fixed; no automatic escalation chain. Status polling and page refresh never trigger new model calls. Optional A5 has lowest priority.

Failures remain bounded

Each logical model generation has at most 3 actual requests total, sharing that ceiling between the initial request, SDK/transport retries, and at most one semantic repair with the same evidence/schema. A repair never gets three new attempts. An invalid third response stops without another repair request. A2 cannot rename a failed step to reset limits; valid next steps also consume the enclosing model/tool-call allowance. Every actual call consumes enclosing token, spend, and time budgets. Refusal/policy blocks stop affected work without bypass attempts. Missing facts remain missing; identity uncertainty uses the existing single evidence recheck. A3 failure prevents scraping; A4 failure preserves raw evidence and other cells; A5 failure only omits the explanation. Stop dependent work on shared authentication, hard-quota, or deployment blockers.

Strict contracts and evaluation

Keep 11 fixed external input contracts and one shared internal result schema. A deterministic serializer handles contract-permitted optional omissions and request packaging; unsupported nulls and internal metadata never enter scraper requests. Reuse accepted normalization only for matching tenant, evidence, context, freshness, and versions. Reuse cannot refresh timestamps or make stale successes retryable. Evaluate identity errors, unsupported facts, contract compliance, coverage, cost, and latency before changing prompts/models or increasing load. The requested A3/Terra and A4/Luna normalization remains the initial policy. Benchmark it against deterministic mapping of structured records; revise that policy explicitly if code produces the same verified output more efficiently. Test typical runs and maximum scope before claiming optimized cost or latency.
